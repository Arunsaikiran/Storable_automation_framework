Framework files

main.py

The entry point: one command, one run, start to end
Why this file exists
The framework already had main.py to run the validators. YAML generation was added as one step before the validators, so the user runs the same command as before and the YAML is made ready automatically. No separate CLI.
Main pieces
  • main.py:14 main(): parses flags, builds paths, runs generation, then the validators, exits 0 / 1 / 2
  • main.py:95 if yaml_generation: check every requested table's YAML against the live structure, rewrite where it differs, keep only ready tables
  • main.py:142 if not yaml_generation: named tables only, create a YAML only when it is missing
  • main.py:202 schema_ctx: schema validation gets the tables as requested; count and data get the ready list
  • main.py:245 exit: 0 all matched, 2 differences, 1 system error or a FAILED table
Who calls it / what it calls
Calls utility.parse_arguments(), generate_yaml.run_for_validation() / tables_missing_yaml(), then the four validators.
If someone asks
Why import yaml_generation inside the if? So a run on silver / reports / sanity never needs the folder. Why exit 1 on a FAILED table? A table we could not build YAML for is a failure, never a silent skip.

utils/utility.py

Shared helpers of the framework: arguments, logging, output paths, summaries, incremental window
Why this file exists
Existing framework file. YAML generation only touched what it needed: the new flags and their defaults. The incremental window helpers here are what fill :start_time and :end_time in the generated SQL.
Main pieces
  • utils/utility.py:447 parse_arguments(): all flags; --yaml_generation and --filter_files default to yes on bronze, no elsewhere (utils/utility.py:572)
  • utils/utility.py:23 get_config_output_paths(): finds the YAML files for the run and where results go
  • utils/utility.py:322 create_summary() and the summary Excel writers: the PASS/FAIL report
  • utils/utility.py:608 check_freshness(): is Snowflake synced recently enough
  • utils/utility.py:634 get_dates(): the window from control_table.csv + Fivetran API
  • utils/utility.py:677 update_control_table(): move the window forward after the check
  • utils/utility.py:701 get_incremental_dates(): freshness + dates in one call
Who calls it / what it calls
Called by main.py and by the validators. Does not call the generator.
If someone asks
Where do incremental dates come from? Not from the workbook: the window is the validators' (control table last sync to Fivetran sync time), applied as updated_at > :start_time AND updated_at <= :end_time.

validators/

The existing checks: schema, count, data (and integrity on sanity)
Why this file exists
Existing framework files. They read the YAML the generator wrote in config/, run the source and Snowflake queries, and compare. YAML generation only makes sure that YAML is there and up to date before they start.
Main pieces
  • validators/schema_validation.py:17 validate_schema(): column structure
  • validators/count_validation.py:40 validate_count(): the two counts must be equal
  • validators/data_validation.py:21 validate_data(): rows sorted by the key, then compared
  • validators/integrity_check.py:40 validate_integrity(): sanity layer only
Who calls it / what it calls
Called by main.py. Uses db/factory.get_database() and, for an incremental run, utility.get_incremental_dates().
If someone asks
How are json columns compared? A generated YAML lists them in json_columns; they are compared as flattened text (utils/json_normalize.py:88).

yaml_generation/ code

yaml_generation/generate_yaml.py

The orchestrator: the only file main.py talks to
Why this file exists
Keeps main.py small. It ties the other files together: read the workbook, group tables, open connections, generate the YAML, and tell main.py which tables are ready.
Main pieces
  • yaml_generation/generate_yaml.py:77 resolve_args(): check flags, fill {env} (DEV, STG, QAT, PRD) into the Snowflake name
  • yaml_generation/generate_yaml.py:98 generate(): per location, per table: columns, reconcile, filters, window, key, write data YAML + count entry
  • yaml_generation/generate_yaml.py:232 config_dir_for(): which config folder a layer and run type writes to
  • yaml_generation/generate_yaml.py:237 tables_missing_yaml(): file check only, no database, for --yaml_generation no
  • yaml_generation/generate_yaml.py:249 workbook_spelling(): use the workbook's spelling of a table name (names ignore case)
  • yaml_generation/generate_yaml.py:261 run_for_validation(): the entry point; returns (results, ready_tables)
Who calls it / what it calls
Called by main.py. Calls filter_files, settings, db_rules, yaml_builder and db/factory.get_database().
If someone asks
Statuses? NEW, UPDATED, UNCHANGED, PRESENT are ready; FAILED is not. Does it delete YAML? Never. Why group by location? One run can hold tables from different schemas or applications on the same engine.

yaml_generation/filter_files.py

The master workbook reader: the one source of truth
Why this file exists
Where each table lives (application, source schema, Snowflake database and schema) and its row filter come from the Excel the team already maintains. Nothing about location is on the command line or in code, so adding a table means adding a row.
Main pieces
  • yaml_generation/filter_files.py:91 WORKBOOKS: postgres = edge_bronze_master.xlsx, mssql = sitelink_bronze_master.xlsx
  • yaml_generation/filter_files.py:96 Location / Row: where a table lives, and its filter cell
  • yaml_generation/filter_files.py:324 read(): reads the layer's workbook, one Row per table; refuses a blank location or a target without {env}
  • yaml_generation/filter_files.py:389 filters(): each filter cell becomes a source WHERE and a Snowflake WHERE
  • yaml_generation/filter_files.py:264 convert() with _plan() yaml_generation/filter_files.py:176 and _where() yaml_generation/filter_files.py:250: joins become col IN (SELECT id FROM ...); the Snowflake side adds _FIVETRAN_ACTIVE = TRUE
  • yaml_generation/filter_files.py:131 Refused: OR, BETWEEN, outer joins, subqueries are refused, not guessed
Who calls it / what it calls
Called by generate_yaml. Uses db_rules for the engine names.
If someone asks
Why filters at all? Big tables (notes 100M rows, account_balance_taxes 35M) cannot be loaded into RAM; the filter keeps a slice, applied the same way on both sides for count and data. Why convert joins? The framework query is one table per side; a sub-select keeps it one table.

yaml_generation/yaml_builder.py

Builds the YAML: column matching, the SQL, the files. No database calls
Why this file exists
Pure logic, so it is easy to unit test. Given two column lists it decides what to compare and writes SQL that turns every value into text the same way on both sides, so PostgreSQL / SQL Server and Snowflake can be compared row by row.
Main pieces
  • yaml_generation/yaml_builder.py:83 check_filter(): refuses ; { } -- /* */ and line breaks (SQL injection guard)
  • yaml_generation/yaml_builder.py:147 incremental_window(): adds > :start_time AND <= :end_time on the window column
  • yaml_generation/yaml_builder.py:179 reconcile(): normalise names, exact match, apply exclusions; a one-sided column is kept with a MISSING token
  • yaml_generation/yaml_builder.py:226 comparability_problems(): types that cannot become text (rowversion) fail the table
  • yaml_generation/yaml_builder.py:261 value_expression(): booleans, timestamps, NULL become the same text on both sides
  • yaml_generation/yaml_builder.py:334 build_data_entry() / yaml_generation/yaml_builder.py:363 build_count_entry(): the two SELECTs and the count queries
  • yaml_generation/yaml_builder.py:466 write_data_file(): writes only when the text changed (NEW / UPDATED / UNCHANGED)
  • yaml_generation/yaml_builder.py:526 upsert_count_file(): adds or replaces this table in the layer's count YAML, keeps the others
Who calls it / what it calls
Called by generate_yaml. Uses db_rules for how to quote and cast per engine.
If someone asks
Why not fuzzy-match columns? A wrong match would hide a real difference. Why a MISSING token instead of dropping the column? Fail, don't skip: the difference shows up in the report.

yaml_generation/db_rules.py

Per-engine rules: how to read a catalogue and how to write a value as text
Why this file exists
PostgreSQL, SQL Server and Snowflake each have different catalogues, quoting and casting. Keeping those differences in one dictionary means a new engine is one new block, not changes all over the code.
Main pieces
  • yaml_generation/db_rules.py:30 RULES: one block per engine (postgres, mssql, snowflake ...)
  • yaml_generation/db_rules.py:145 kind_of(): data type to kind (text, number, boolean, timestamp, json)
  • yaml_generation/db_rules.py:169 quote(): quote a name the engine's way
  • yaml_generation/db_rules.py:185 list_tables(): is the schema visible? An empty listing is refused
  • yaml_generation/db_rules.py:201 list_columns(): pg_catalog for PostgreSQL, INFORMATION_SCHEMA otherwise
  • yaml_generation/db_rules.py:223 primary_key_columns(): the rules workbook key wins, else the source primary key
Who calls it / what it calls
Called by generate_yaml (catalogue reads) and yaml_builder (casting).
If someone asks
Why pg_catalog? It shows columns and keys even where INFORMATION_SCHEMA hides them for our role. No primary key? The data YAML FAILS with a log line; the count is still written.

yaml_generation/settings.py

The optional settings you edit: exclusions and table rules
Why this file exists
Things that are not a location: columns to leave out and per-table overrides (key, filters, window column). Optional: without them the run is normal.
Main pieces
  • yaml_generation/settings.py:64 load_exclusions(): settings/exclusions.yaml, the engine's section + snowflake (Fivetran columns)
  • yaml_generation/settings.py:83 load_table_rules(): rows of the rules workbook per engine and schema
  • yaml_generation/settings.py:141 pick_rules_file(): the one .xlsx in settings/ (dev_rules.xlsx)
  • yaml_generation/settings.py:43 INCREMENTAL_COLUMNS: updated_at for postgres, dupdated for mssql
Who calls it / what it calls
Called by generate_yaml.
If someone asks
Which filter wins? A filter in the rules workbook beats the filter workbook for the same side. Why exclude Fivetran columns? They exist only in Snowflake (_FIVETRAN_SYNCED, ...).

yaml_generation/ data and tests

master_files/*.xlsx

edge_bronze_master.xlsx, sitelink_bronze_master.xlsx
Why this file exists
The data behind filter_files.py: one row per table.
Main pieces
  • Target Table Name, source_application, source_database (the real database: fms, DevT5000), source_schema, target_application, target_database ({env}_...), target_schema
  • Historical / Incremental filter cells (optional)
Who calls it / what it calls
Read by filter_files.read()
If someone asks
Add a table? Add a row. Add an application on a known engine? Its rows in that layer's workbook, if the connection can reach it. The step-by-step tab checks that.

settings/: exclusions.yaml, dev_rules.xlsx, templates/

The settings files
Why this file exists
The data behind settings.py.
Main pieces
  • exclusions.yaml: columns left out, per engine
  • dev_rules.xlsx: per-table key, exclusions, filters
  • templates/table_rules_template.xlsx: blank copy to start from
Who calls it / what it calls
Read by settings.py
If someone asks
Why a template? So a new rules file has the right headers.

config/<run_type>/<layer>/

The YAML the generator writes and the validators read
Why this file exists
The hand-off between the two halves of a run: yaml_builder.py writes here, the validators read from here.
Main pieces
  • data_validation/<table>.yaml: one file per table, the two normalised SELECTs
  • count_validation/<layer>.yaml: one file per layer, one entry per table
Who calls it / what it calls
Written by yaml_builder (write_data_file(), upsert_count_file()); found by utility.get_config_output_paths().
If someone asks
Is old YAML deleted? Never. A table no longer in the workbook is logged and left as it is.

tests/

Unit tests and scenario cases (pytest)
Why this file exists
Each module has its own test file, so a change can be checked without a database.
Main pieces
  • test_filter_files, test_generate_yaml, test_yaml_builder, test_db_rules, test_settings, test_json_normalize
  • test_connections, test_live_postgres: need real database access
  • cases/ + CASES.md: end-to-end scenarios (what if the Excel says ...)
Who calls it / what it calls
Run with pytest yaml_generation/tests
If someone asks
How do we know it works? Unit tests + scenario cases + the integration runs in YAML_GENERATION_TEST_ISSUES.md.
